# مواصفة التصميم: الربط الجماعي للفواتير + تقرير كارت الصنف

**التاريخ:** 2026-06-14
**المشروع:** أداة مطابقة المشتريات والمبيعات (PBK)
**الحالة:** مُعتمد للتخطيط

---

## ١. الهدف

ميزتان مطلوبتان في نفس المواصفة:

1. **الربط الجماعي (many-to-one / one-to-many):** ربط أكتر من فاتورة شراء على فاتورة بيع واحدة، أو فاتورة شراء واحدة على أكتر من فاتورة بيع (وكمان حالات N:M يدوياً). مثال من الواقع في شاشة المطابقة: سطرَا شراء «كرتون نموذج 2» بكميتي **28,634 + 916** يتربطوا على سطر بيع واحد بكمية **29,550** — يطابقوا بفرق **صفر**.

2. **تقرير كارت الصنف (كارت صنف / Stock Card):** لكل صنف، كشف زمني بالوارد (مشتريات) والمنصرف (مبيعات) والرصيد المتبقي في المخزن.

---

## ٢. السياق الحالي (قبل التعديل)

- **الربط 1:1 إجباري.** جدول `matches` في [app/db.py](../../../app/db.py) فيه `purchase_line_id ... UNIQUE` **و** `sale_line_id ... UNIQUE` — ده اللي بيمنع الربط الجماعي.
- **قاعدة بيانات بطبقتين** (SQLite محلياً / Postgres على Vercel) عن طريق shim في `db.py`: ثوابت `_PK`/`_REAL`/`_NOW` حسب الـbackend، تحويل `?`→`%s`، وإضافة `RETURNING id` تلقائياً لجداول `_ID_TABLES`.
- **قالب Excel (Table1، أعمدة A–T):** كل صف بيقابل سطر شراء واحد (A–I) بسطر بيع واحد (J–R)، والصنف مشترك في العمود D، وفرق الكمية في `T = E-N`. **المهم:** كل الإجماليات (`SUBTOTAL` على الأعمدة، و`J2=Q4-H4` لصافي الضريبة، و`R2=R4-I4`) بتجمع **أعمدة كاملة**، فهي مظبوطة بغض النظر عن طريقة الربط أو ترتيب الصفوف.
- **التطبيع العربي:** `normalize_ar()` في [app/matching.py](../../../app/matching.py) بيوحّد الهمزات (أ/إ/آ→ا)، ة→ه، ى→ي، ئ→ي، ؤ→و، ويشيل التشكيل والتطويل والترقيم. هنعيد استخدامه في تجميع الأصناف.
- **إشارة الإشعارات الدائنة:** الإشعارات الدائنة متخزّنة بكمية **سالبة** في التطبيق.

## الميزة ١: الربط الجماعي للفواتير

### ٣.١ نموذج البيانات (الطريقة المعتمدة: جدول مجموعات)

نستبدل جدول `matches` بنموذج «مجموعة مطابقة» يعمّم الحالة 1:1 (اللي بتبقى مجرد مجموعة فيها سطر شراء واحد + سطر بيع واحد):

```sql
CREATE TABLE IF NOT EXISTS match_groups (
    id {_PK},
    note TEXT DEFAULT '',
    created_at TEXT DEFAULT {_NOW}
);
CREATE TABLE IF NOT EXISTS match_group_purchases (
    group_id INTEGER NOT NULL REFERENCES match_groups(id) ON DELETE CASCADE,
    purchase_line_id INTEGER NOT NULL UNIQUE REFERENCES purchase_lines(id) ON DELETE CASCADE,
    PRIMARY KEY (group_id, purchase_line_id)
);
CREATE TABLE IF NOT EXISTS match_group_sales (
    group_id INTEGER NOT NULL REFERENCES match_groups(id) ON DELETE CASCADE,
    sale_line_id INTEGER NOT NULL UNIQUE REFERENCES sale_lines(id) ON DELETE CASCADE,
    PRIMARY KEY (group_id, sale_line_id)
);
```

**الثوابت الدلالية (invariants):**
- `UNIQUE` على `purchase_line_id` و`sale_line_id` → كل سطر ينتمي لمجموعة واحدة على الأكثر (نفس مبدأ «السطر يتطابق مرة واحدة» المهم للمصالحة الضريبية).
- المجموعة الصالحة لازم تحتوي **سطر شراء واحد على الأقل وسطر بيع واحد على الأقل**. لو حذف سطر خلّى مجموعة من غير أي طرف، المجموعة تتحذف ويرجع الطرف الباقي «غير مرتبط» (يتنفّذ في منطق التطبيق بعد الحذف/فك الربط).
- `ON DELETE CASCADE` بيحافظ على نفس سلوك الحذف الحالي عبر الـbackend-ين.
- العمودان من نوع `INTEGER` يشيران إلى `id` من نوع `BIGINT` في Postgres — نفس النمط المُطبَّق فعلاً في جدول `matches` الحالي والمنشور، فهو متوافق.

**تعديلات `db.py`:**
- إضافة الجداول التلاتة لـ`SCHEMA` (بـ`CREATE TABLE IF NOT EXISTS`).
- إضافة `"match_groups"` لمجموعة `_ID_TABLES` (عشان `RETURNING id` يشتغل في Postgres). جدولا العضوية **مايتضافوش** (مفيش عمود `id`، المفتاح مركّب).
- حذف تعريف `matches` من `SCHEMA` (التثبيتات الجديدة مش محتاجاه)؛ التعامل مع التثبيتات القديمة عن طريق الترقية أدناه.

### ٣.٢ ترقية البيانات (Migration)

دالة `_migrate_matches_to_groups(conn)` تُستدعى داخل `init_db()` بعد `executescript(SCHEMA)` وعلى **نفس الاتصال**، **idempotent** (تتنفّذ بأمان أكتر من مرة):

1. **تتحقق من وجود جدول `matches` أولاً** قبل أي `SELECT` منه — عن طريق `sqlite_master` في SQLite و`to_regclass('matches')` في Postgres (تفرّع على `db.USE_PG`). لو مش موجود (تثبيت جديد) → ترجع بهدوء. **مهم:** ما نعتمدش على try/except حوالين `SELECT FROM matches`، لأن فشل العبارة في Postgres بيُفسد المعاملة المفتوحة اللي بتعمل إنشاء الجداول كمان.
2. لو `match_groups` فيها صفوف بالفعل → ترجع (الترقية اتعملت قبل كده).
3. لكل صف في `matches`: تنشئ `match_groups` (تاخد `group_id` من `lastrowid`)، وتدخل صف في `match_group_purchases` وصف في `match_group_sales`، وتنقل `note`.
4. `DROP TABLE matches` (DDL معامَلاتي في الـbackend-ين).

يشتغل في الـbackend-ين: `INSERT INTO match_groups(...)` بياخد `RETURNING id` تلقائياً في Postgres فيشتغل `lastrowid` زي SQLite.

> البيانات الحالية كلها قابلة لإعادة الاستيراد من Excel/ETA، فالترقية منخفضة المخاطر؛ ومع ذلك تتم بدون فقد بيانات.

### ٣.٣ واجهات API

| الـEndpoint | قبل | بعد |
|---|---|---|
| `GET /api/matches` | صفوف أزواج | قائمة مجموعات: `[{id, note, purchases:[line...], sales:[line...], purchase_qty, sale_qty, qty_diff, created_at}]` حيث `qty_diff = Σ purchase.qty − Σ sale.qty` |
| `POST /api/matches` | `{purchase_id, sale_id, note}` | `{purchase_ids:[...], sale_ids:[...], note}` — يتحقق: ≥1 من كل جنب، ومفيش سطر مرتبط بمجموعة تانية (وإلا 409)، وكل المعرفات موجودة (وإلا 404)؛ ينشئ مجموعة + عضويات في معاملة واحدة |
| `DELETE /api/matches/{group_id}` | يحذف زوج | يحذف المجموعة (cascade على العضويات)؛ السطور ترجع غير مرتبطة |
| `POST /api/matches/auto` | اقتراحات 1:1 | اقتراحات موحّدة (1:1 ومجموعات) — انظر ٣.٤ |
| `POST /api/matches/accept` | `{pairs:[{purchase_id, sale_id}]}` | `{groups:[{purchase_ids, sale_ids, note}]}` — ينشئ كل مجموعة، يتخطى المتعارض |

**Endpoints متأثرة (تعديل غير مباشر):**
- `GET /api/lines` (دالة `list_lines`): فلتر `matched` و عمود `match_id` لازم يعتمدوا على عضوية المجموعات بدل `matches`. يرجع `group_id` بدل `match_id`. (الواجهة بتستخدمه لشارة «مرتبط» وللتبويبات «غير مرتبطة».)
- `GET /api/dashboard`: `matches_count` → عدد المجموعات؛ `unmatched_purchases`/`unmatched_sales` → سطور مش في أي عضوية؛ `qty_mismatch_count` → عدد المجموعات اللي `|Σp − Σs| > 0.001`.

### ٣.٤ المطابقة التلقائية للمجموعات (auto-discovery)

تعديل `auto_match()` في `matching.py` ليرجع نوعين من الاقتراحات:

**الخطوة ١ — أزواج 1:1 (زي الحالي):** الخوارزمية الجشعة الحالية بـ`score_pair ≥ MATCH_THRESHOLD`.

**الخطوة ٢ — اكتشاف المجموعات** على السطور المتبقية غير المرتبطة بعد الخطوة ١:
- تقسيم السطور المتبقية حسب **مفتاح الصنف المعياري** (`normalize_ar(item)`). الدمج بس داخل نفس الصنف المعياري.
- داخل كل صنف:
  - لكل فاتورة بيع متبقية: ابحث عن **مجموعة جزئية من المشتريات** (حجمها 2..K، حيث `K=4`) في **نافذة تاريخية** (مشتريات خلال `±D` يوم من تاريخ البيع، `D=60`) مجموع كمياتها ≈ كمية البيع بسماحية `tol = max(0.02 × |sale.qty|, ε)`. (subset-sum)
  - بشكل متماثل: لكل فاتورة شراء، مجموعة جزئية من المبيعات تساوي كمية الشراء.
- **جشع:** أول ما سطر يُستخدم في مجموعة مقترحة، يُستبعد من البحث التالي.
- **حدود الأداء:** لو عدد مرشّحي الصنف الواحد > 12، نقتصر على الأقرب تاريخياً (12)؛ مع `K=4` ده على الأكثر `C(12,4)=495` تركيبة لكل فاتورة — رخيص.
- التلقائي يكتفي بـ **N:1 و 1:N** فقط؛ حالات N:M المعقّدة تُترك للربط اليدوي.

**شكل الاقتراح الموحّد** (لكل من 1:1 والمجموعات): `{purchase_ids:[...], sale_ids:[...], purchases:[line...], sales:[line...], score, qty_diff}`. الواجهة تعرضها وزرار «اعتماد» يبعتها لـ`/api/matches/accept`.

> الثوابت `K`، `D`، `tol`، حد المرشّحين قابلة للضبط ومُعرّفة كثوابت في أعلى `matching.py`.

### ٣.٥ واجهة المستخدم (شاشة المطابقة)

في [static/index.html](../../../static/index.html) و[static/app.js](../../../static/app.js):
- **اختيار متعدد:** استبدال `radio` بـ`checkbox` في جدولَي «مشتريات غير مرتبطة» و«مبيعات غير مرتبطة». الحالة `selP`/`selS` تبقى **مجموعتين (Set)** من المعرفات.

- زرار «ربط» يبعت كل المؤشَّر كمجموعة واحدة لـ`POST /api/matches`. يتعطّل لو طرف فاضي.
- **جدول «المطابقات الحالية»** يعرض كل مجموعة كـ«بلوك» (سطورها مكدّسة) + صف إجمالي للمجموعة (مجموع الشراء/البيع/الفرق) + زرار «فك الربط» للمجموعة كلها.
- شارة «مرتبط» في تبويبات المشتريات/المبيعات تعتمد على `group_id`.

### ٣.٦ التصدير/الاستيراد (Excel)

تعديل `export_workbook()` في [app/excel_io.py](../../../app/excel_io.py) ليستقبل مجموعات بدل أزواج:
- **الإجماليات تفضل مظبوطة 100%** (لأنها `SUBTOTAL` على أعمدة كاملة، مستقلة عن التجميع).
- كل مجموعة تتصدّر كـ**بلوك صفوف متتالية**: سطور الشراء (A–I) بمحاذاة سطور البيع (J–R)؛ الطرف الأقصر يسيب خلايا فاضية؛ الصنف في D من المجموعة. صفوف المجموعة المتعددة الـ`T = E−N` تجمع لفرق المجموعة الصحيح.
- ترتيب الصفوف: بلوكات المجموعات، ثم المشتريات غير المرتبطة، ثم المبيعات غير المرتبطة (زي الحالي).
- (اختياري — تحسين بصري) تظليل خفيف متناوب لكل بلوك مجموعة.

**حد معروف:** إعادة استيراد ملف فيه مجموعات متعددة بترجّعها أزواج 1:1 (الاستيراد بيقرن صف-بصف؛ السطور المكدّسة الزيادة بتبقى غير مرتبطة). مقبول لأن قاعدة البيانات نفسها بتحفظ المجموعات، والـExcel للمشاركة والتقارير. (`import_workbook` يفضل زي ما هو؛ `import_excel` يبني مجموعة 1:1 لكل زوج صف.)

## الميزة ٢: تقرير كارت الصنف

تقرير **للقراءة فقط**، مستقل تماماً عن المطابقة — بيشتغل على كل سطور المشتريات والمبيعات.

### ٤.١ نموذج القراءة وتجميع الأصناف

- **مفتاح الصنف** = `normalize_ar(item)`. الأصناف اللي بتختلف في الإملاء البسيط (همزات/تشكيل/مسافات) تتجمّع في كارت واحد، لكن «نموذج 1» و«نموذج 2» يفضلوا منفصلين (لأن التطبيع بيساوي النصوص بعد التطبيع، مش تشابه ضبابي).
- **عنوان الصنف المعروض** = أكثر تهجئة أصلية تكراراً ضمن المفتاح (وإلا الأطول).

### ٤.٢ حساب الحركة والرصيد (التعامل مع الإشارة)

لكل حركة، **الأثر على المخزون** `e`:
- سطر شراء: `e = +qty`
- سطر بيع: `e = −qty`

ثم العرض في عمودين موجبين دايماً + رصيد تراكمي:
- لو `e > 0` → `وارد += e`
- لو `e < 0` → `منصرف += −e`
- `balance += e`

ده بيخلّي الإشعارات الدائنة (المخزّنة بالسالب) تقع تلقائياً في العمود المعاكس الصحيح:
- إشعار دائن مشتريات (مرتجع للمورد، `qty<0`) → `e<0` → يظهر **منصرف** (يقلّل المخزون). ✅
- إشعار دائن مبيعات (مرتجع من العميل، `qty<0`) → `e = −qty > 0` → يظهر **وارد** (يرجّع للمخزون). ✅

**تسمية الحركة** حسب النوع والإشارة: «شراء» / «إشعار دائن مشتريات» / «بيع» / «إشعار دائن مبيعات».
**الترتيب:** بالتاريخ ثم بالـ`id` (السطور بدون تاريخ في الآخر، زي ترتيب `list_lines`).

### ٤.٣ واجهات API

| الـEndpoint | الوصف |
|---|---|
| `GET /api/stock-card` | نظرة عامة: `[{item_key, item_label, total_in, total_out, balance, movements_count}]` مرتّبة بالعنوان |
| `GET /api/stock-card/item?key=<norm>` | كشف صنف واحد: `{item_label, rows:[{date, kind:'in'|'out', label, invoice_no, party, qty_in, qty_out, balance, source, doc_type, note}], total_in, total_out, balance}` |

> المفتاح المعياري ممكن يحتوي مسافات/عربي، فبيتبعت كـ**query parameter** مش path.

### ٤.٤ واجهة المستخدم (تبويب جديد «كارت الصنف»)

- زرار جديد في الـrail (`data-tab="stockcard"`) + قسم `section.tab#tab-stockcard` + دالة `loadStockCard()` في `app.js` (نفس نمط التبويبات الحالي).
- **قائمة الأصناف:** صندوق بحث + جدول (الصنف، وارد، منصرف، الرصيد). الضغط على صف بيحمّل الكشف.
- **كشف الصنف:** جدول (التاريخ، الحركة، رقم الفاتورة، الطرف، وارد، منصرف، الرصيد) + إجماليات أسفله + زرار «تصدير Excel» للصنف ده.

### ٤.٥ تصدير Excel لكارت الصنف

دالة جديدة `export_stock_card()` في `excel_io.py` (RTL، بنفس روح القالب: رؤوس ملوّنة، تنسيق أرقام `#,##0`):
- **ورقة كارت الصنف:** رأس باسم الصنف، أعمدة (التاريخ، الحركة، رقم الفاتورة، الطرف، وارد، منصرف، الرصيد)، صف إجماليات.
- **التصدير الكامل:** ورقة «نظرة عامة» (كل الأصناف بإجمالياتها) + ورقة لكل صنف.

## ٥. الاختبارات (TDD)

كل الـ48 اختبار الحالية تفضل خضراء (بعد تحديث الاختبارات المرتبطة بشكل `matches` القديم).

**اختبارات جديدة:**
- **`matching.py`:** اكتشاف المجموعات يلاقي 28,634+916=29,550؛ مايدمجش أصناف مختلفة؛ يحترم النافذة التاريخية؛ يحترم حد الحجم K؛ ما يقترحش مجموعة كمياتها بعيدة.
- **الترقية (`db.py`، SQLite):** صفوف `matches` القديمة تتحوّل لمجموعات صحيحة؛ idempotent؛ تثبيت جديد ما يحاولش يرحّل.
- **API المطابقة:** إنشاء مجموعة N:1 و1:N وN:M؛ رفض سطر مرتبط بالفعل (409)؛ رفض طرف فاضي؛ حذف مجموعة يرجّع السطور غير مرتبطة؛ auto+accept ينشئ مجموعات؛ عدّادات الـdashboard.
- **كارت الصنف:** إجماليات النظرة العامة؛ الرصيد التراكمي مع انعكاس إشارة الإشعارات الدائنة؛ تجميع التهجئات المتقاربة في مفتاح واحد وفصل «نموذج 1/2».
- **Excel:** تصدير فيه مجموعة متعددة يحافظ على صحة `SUBTOTAL`/`J2`/`R2` (امتداد لأسلوب [tests/verify_export.py](../../../tests/verify_export.py))؛ بنية ورقة كارت الصنف.

## ٦. الحدود والمخاطر

- إعادة استيراد مجموعة متعددة من Excel بترجّعها 1:1 (القاعدة بتحفظ المجموعات؛ الحد موثّق).
- الاكتشاف التلقائي للمجموعات محدود بـ N:1 و1:N (N:M يدوي).

- الترقية تحذف جدول `matches`؛ غير قابلة للرجوع (لكن البيانات قابلة لإعادة الاستيراد).

## ٧. مراحل التنفيذ المقترحة

المرحلتان مستقلتان (ممكن أي ترتيب؛ كارت الصنف معزول تماماً وممكن يتشحن أولاً كمكسب سريع):

- **المرحلة ١ — الربط الجماعي:** جداول `db.py` + الترقية → تعديل `matching.py` (اكتشاف المجموعات) → endpoints المطابقة + `list_lines` + `dashboard` → واجهة المطابقة (اختيار متعدد + شريط حي) → تصدير Excel بالبلوكات → الاختبارات.
- **المرحلة ٢ — كارت الصنف:** نموذج القراءة + التطبيع → endpoints كارت الصنف → التبويب والواجهة → تصدير Excel → الاختبارات.

**نطاق الملفات:** `app/db.py`، `app/matching.py`، `app/main.py`، `app/excel_io.py`، `static/index.html`، `static/app.js`، `static/style.css`، `tests/*`.
